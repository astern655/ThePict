# 요구분석 문서 — YOLO-pose 기반 헬스 자세 교정 앱

- 버전: v0.3 (2026-07-17) — 기초 기능 표준화(운동 가이드·로그인·온보딩·프로필) 반영, Q4 "계정 도입" 확정
- 상태: 초안 (잔여 열린 질문 확정 전)
- 스택: 프론트엔드 Flutter / 백엔드 FastAPI / AI YOLO-pose (관절 키포인트 추정)

> 용어 참고: 사용자 요청의 "YOLO 객체탐지"는 바운딩박스 탐지만으로는 자세 교정이 불가능하므로, **YOLO-pose(키포인트 추정)** 로 재해석했다. 키포인트로 관절 각도·정렬을 계산해 폼을 판정한다.

> v0.3 변경 요지: 사용자 지시("운동 방법·기초 기능은 기존 헬스 앱을 따라갈 것, 로그인 포함")에 따라 F11(운동 가이드)·F12(로그인/온보딩)·F13(프로필/설정)을 MVP에 추가. **Q4가 "계정 도입"으로 확정되어 FastAPI 서버 + 서버 DB가 MVP 필수로 승격** — 종전 "서버 없는 MVP" 권장안은 폐기하고, "온디바이스 추론(유지) + 서버 인증/프로필 + 세션 기록 로컬·서버 동기화(권장)" 하이브리드로 재설계.

## 0. 벤치마킹 근거 — 기존 헬스 앱 표준 패턴

기초 기능(F11~F13)의 정의 근거. 삼성헬스 / Nike Training Club / 플랜핏 / 다노핏·버핏 등 대표 앱의 공통 패턴 기반.

> 조사 방식 주의: 실시간 웹 검색 미수행(권한 미승인). 널리 알려진 표준 UX 패턴 및 App Store 정책에 대한 도메인 지식(~2025) 기반이므로, 특정 앱의 최신 세부 사양이 결정에 중요하면 재조사 필요.

- **운동 가이드**: 운동별 상세 페이지(운동명·타깃 부위·난이도) + 시연 미디어(루프 애니메이션/영상) + 동작 단계 텍스트(시작→동작→복귀) + 주의사항/흔한 실수 + 부위·기구·난이도 필터.
- **로그인/온보딩**: 소셜 로그인이 표준 — **iOS는 Apple 로그인 필수**(소셜 로그인 제공 시 App Store 심사 규정), Android/공통은 Google, 국내 앱은 카카오 추가가 흔함, 이메일은 폴백. 온보딩에서 성별·나이·키·몸무게·목표·운동 경험을 받아 개인화 기반으로 사용.
- **기초 표준**: 프로필(신체정보·목표 수정), 설정(알림·단위·약관·로그아웃·**계정/데이터 삭제** — 스토어 정책상 사실상 필수), 운동 리마인더 알림(2차 권장).
- 커뮤니티 피드·식단·웨어러블·챌린지는 표준이지만 우리 범위 제외와 일치 → 미채택.

## 1. 핵심 사용자 시나리오

대표 페르소나: 혼자 헬스장/홈트를 하는 중급 이하 사용자. 트레이너 없이 운동하며, 자세가 맞는지 불안하고, 부상 없이 정확한 폼을 익히고 싶다.

### 시나리오 A — 실시간 폼 코칭 (주력)
1. 앱 실행(로그인 상태 유지) → 오늘 할 운동으로 "스쿼트" 선택
2. (처음 하는 운동이면) 운동 가이드에서 동작 방법·주의사항 확인 (F11)
3. 거치대에 폰을 세우고 카메라 조준 (전신 프레이밍 가이드 표시)
4. 운동 시작 → 실시간 키포인트 추출, 스켈레톤 오버레이 표시
5. 무릎이 발끝을 넘거나 허리가 굽으면 즉시 시각·음성 피드백 (운동 중 화면을 볼 수 없으므로 음성 필수)
6. 세트 종료 → 세트 요약 (총 렙 수, 좋은 폼 비율, 자주 틀린 부분)

### 시나리오 B — 녹화 후 정밀 리뷰 (비실시간)
1. 운동 1세트를 앱으로 녹화 (또는 갤러리 영상 업로드)
2. 분석 요청 → 처리 중 표시
3. 결과: 렙별 타임라인, 렙별 폼 점수, 문제 구간을 프레임 단위로 지적
4. 문제 구간을 스켈레톤 오버레이와 함께 재생하며 복기

### 시나리오 C — 렙 카운팅 + 기록 + 어제와 비교
1. 운동 중 앱이 자동으로 반복 횟수 카운트
2. 세션 종료 시 운동별 세트/렙/폼 점수가 날짜별 기록으로 저장 (로컬 우선, 서버 동기화)
3. 캘린더 탭에서 운동한 날짜 확인, 날짜 선택 시 그날 세션 상세 조회
4. 오늘 세션 요약에서 "어제(직전 세션) 대비" 렙 수·폼 점수·운동량 증감 확인

### 시나리오 D — 첫 사용 (온보딩)
1. 앱 설치 → 소셜(Apple/Google) 또는 이메일로 가입 (F12)
2. 온보딩: 성별·나이·키·몸무게·목표 입력 → 프로필 생성
3. 홈 진입 → 지원 운동 목록과 가이드 확인 후 첫 운동 시작

> 시나리오 A(실시간)와 B(녹화 리뷰)는 기술 아키텍처가 완전히 다르다. A는 저지연 필수 → 온디바이스 유리, B는 지연 허용 → 서버 추론 가능. 둘 다 MVP에 넣으면 파이프라인이 2개가 된다 → Q1·Q2에서 확정 필요.

## 2. MVP 기능 목록

### F1. 카메라 촬영 & 프레임 캡처
- 설명: 운동 자세를 카메라로 촬영하고 추론용 프레임을 확보한다. 전신 프레이밍/거리 가이드 오버레이 포함.
- 담당: **Flutter**
- 수용 기준:
  - 후면/전면 카메라 전환 가능, 전신이 프레임에 들어오는지 가이드가 표시된다.
  - 촬영 중 프레임이 끊김 없이 캡처되어 추론 파이프라인으로 전달된다.

### F2. 포즈 키포인트 추출 (YOLO-pose 추론)
- 설명: 프레임에서 관절 키포인트(예: COCO 17 keypoints)를 좌표+신뢰도로 추출한다.
- 담당: **AI 모델** (실행 위치는 Q1에 종속: 앱 내 tflite 또는 FastAPI 서버)
- 수용 기준:
  - 단일 인물의 주요 관절 키포인트가 좌표+신뢰도와 함께 반환된다.
  - 사람이 없거나 신뢰도가 낮으면 "인식 실패" 상태를 명확히 반환한다.

### F3. 자세 평가 로직 (각도·정렬 규칙)
- 설명: 키포인트로부터 관절 각도/정렬을 계산해 운동별 규칙으로 폼을 판정하고, 세트 단위 **폼 점수**를 산출한다.
- 담당: **AI 후처리** (온디바이스면 앱 내 로직, 서버면 FastAPI — Q1 종속)
- 수용 기준:
  - 최소 1종 운동(스쿼트)에 대해 무릎/고관절/허리 각도를 계산하고 정상/경고를 구분한다.
  - 판정 규칙(임계 각도 등)이 하드코딩이 아닌 운동별 설정으로 분리돼 있다.
  - 세트별 폼 점수(예: 좋은 폼 비율)가 산출되어 F6 저장 대상이 된다.

### F4. 실시간 피드백 (오버레이 + 텍스트 + 음성)
- 설명: 스켈레톤 오버레이, 문제 관절 색상 강조, 텍스트, **음성 안내**로 즉시 교정 신호를 준다.
- 담당: **Flutter**
- 수용 기준:
  - 키포인트 위에 스켈레톤이 그려지고, 문제 관절이 색상으로 강조된다.
  - 잘못된 자세 발생 시 음성(및 텍스트) 피드백이 지연 없이 제공된다 — 운동 수행 중 화면을 볼 수 없는 상황을 기본으로 가정.

### F5. 렙(반복) 카운팅
- 설명: 운동 동작의 반복 횟수를 자동 계수한다.
- 담당: **AI 후처리** + **Flutter**(표시)
- 수용 기준:
  - 스쿼트 기준 정상 반복에 대해 카운트가 실제 횟수와 대체로 일치한다 (허용 오차 수치는 Q6에서 확정).
  - 세트 종료 시 총 렙 수가 표시되고, **F6에 영구 저장된다** (F9·F10의 성립 조건).

### F6. 세션 기록 저장 & 요약
- 설명: 한 세션의 기록을 **날짜별로** 영구 저장하고 요약을 보여준다. F9·F10의 데이터 기반.
- 담당: **Flutter** + **DB(로컬)** + **FastAPI/서버 DB**(동기화 — 저장 전략은 Q14 종속)
- 저장 항목(스키마 최소 요건): 운동명, 날짜·시각, 세트 수, 세트별 렙 수, 세트별 폼 점수(F3 산출), 세션 시간. **F9가 비교하는 모든 지표(렙 수·폼 점수·운동량)는 이 저장 항목에서 계산 가능해야 한다.**
- 저장 전략 (기획팀 권장, Q14에서 확정): **로컬 우선 + 서버 백그라운드 동기화** — 오프라인(헬스장 네트워크 불안정, Q10)에서도 기록·조회 가능, 로그인 계정으로 백업·기기 이관(Q12 해소).
- 수용 기준:
  - 세션 종료 시 운동명·렙 수·좋은 폼 비율이 요약으로 표시된다.
  - 앱을 껐다 켜도 지난 세션 기록이 날짜별로 남아 있다.
  - (동기화 채택 시) 네트워크가 없어도 기록·조회가 되고, 연결 시 서버로 동기화된다.

### F7. 운동 선택 & 홈 화면
- 설명: 지원 운동 목록에서 오늘 할 운동을 고르고 시작한다. 각 운동에서 가이드(F11)로 진입 가능.
- 담당: **Flutter**
- 수용 기준:
  - MVP 지원 운동 목록이 노출되고 선택 후 촬영 화면으로 진입한다.
  - 미지원 운동은 "준비 중"으로 명확히 구분된다.

### F8. 백엔드 추론 API *(조건부)*
- 설명: 영상/프레임을 받아 키포인트·평가 결과를 반환하는 엔드포인트.
- 담당: **FastAPI** + **AI 모델**
- 포함 조건: **서버 추론(Q1) 또는 녹화 리뷰(Q2)를 MVP에 넣기로 결정한 경우에만.** (주의: v0.3부터 FastAPI 서버 자체는 인증·프로필 용도로 MVP 필수가 되었으나, **추론 API는 여전히 조건부** — 서버가 있다고 추론을 서버로 옮길 이유는 없음.)
- 수용 기준:
  - 프레임/영상 업로드 시 키포인트·폼 판정 결과를 정해진 스키마로 반환한다.
  - 처리 실패(사람 미인식, 포맷 오류)를 명확한 에러로 응답한다.

### F9. 일간 비교 분석 (어제 vs 오늘) — 사용자 요청, 조건부 MVP 편입
- 설명: 같은 운동에 대해 어제(또는 직전 세션 — Q11) 대비 오늘의 렙 수·폼 점수·운동량 증감을 방향(↑/↓/−)+수치로 보여준다.
- 담당: **DB**(날짜별 집계 조회) + **Flutter**(비교 카드 UI) + (서버 집계 채택 시 **FastAPI** 엔드포인트)
- 선행 조건: **F6.** 비교할 과거 데이터가 없으면 성립하지 않음. 비교 지표 3종은 모두 F6 저장 항목에서 계산된다 (상류 신규 요구 없음).
- 수용 기준:
  - 동일 운동에 대해 비교 기준 시점 대비 총 렙 수·평균 폼 점수·운동량의 증감이 방향+수치로 표시된다.
  - 비교할 과거 기록이 없으면(첫 사용, 해당 운동 첫 기록) "비교할 데이터가 없습니다" 빈 상태를 안내한다.
  - 하루에 같은 운동을 여러 세션 수행한 경우의 집계 규칙(합산/최고/평균)은 Q11에서 확정하며, 확정 전 기본값은 **일 합산**으로 한다.

### F10. 캘린더 기록 뷰 — 사용자 요청, MVP 편입 권장
- 설명: 날짜별 운동 기록 유무·요약을 월간 캘린더 뷰로 조회하고, 날짜 선택 시 해당일 세션 상세로 진입한다.
- 담당: **Flutter**(캘린더 UI) + **DB**(날짜 인덱스 조회) + (서버 조회 채택 시 **FastAPI** 엔드포인트)
- 선행 조건: **F6.**
- 수용 기준:
  - 운동한 날짜가 캘린더에 마킹되고, 날짜 선택 시 그날의 세션 요약을 볼 수 있다.
  - 기록이 없는 날짜는 빈 상태로 구분된다.
  - 세션의 소속 날짜는 **세션 시작 시각의 기기 로컬 시간대 기준 달력 날짜**로 기록 시점에 확정한다 (자정을 넘겨 끝난 세션도 시작일 소속, 이후 기기 시간대가 바뀌어도 마킹이 흔들리지 않음). 세부 규칙 이견은 Q11에서 재확정 가능.

### F11. 운동 가이드 (운동 방법·기초 설명) — 사용자 요청(기존 앱 표준 준수), MVP 편입
- 설명: 지원 운동별로 시연 미디어(애니메이션/영상)·동작 단계 텍스트·타깃 부위·주의사항(흔한 실수)을 제공하는 정적 가이드.
- 담당: **Flutter**(가이드 화면·미디어 재생) + **콘텐츠**(운동 데이터·미디어 에셋 — MVP는 앱 로컬 번들 권장, 서버 CMS는 2차)
- 수용 기준:
  - MVP 지원 운동 각각에 대해 타깃 부위·동작 단계·시연 미디어·주의사항이 표시된다.
  - 운동 선택 화면(F7)에서 각 운동의 가이드로 진입할 수 있다.
- 비고: 시연 미디어의 확보 방식(자체 제작 vs 라이선스)은 Q13에서 확정. 주의사항 콘텐츠는 F3의 자세 판정 규칙과 일관되어야 함(가이드가 "이렇게 하라"는 것과 판정이 "틀렸다" 하는 기준이 어긋나면 안 됨).

### F12. 회원가입/로그인 + 온보딩 — 사용자 확정 지시, MVP 편입
- 설명: 소셜/이메일 로그인으로 계정을 만들고, 온보딩에서 신체정보·목표를 받아 프로필을 초기화한다.
- 담당: **Flutter**(로그인·온보딩 UI) + **FastAPI**(인증·토큰 발급/검증) + **서버 DB**(계정·프로필)
- 소셜 구성 권장안 (MVP 최소형): **Apple 로그인(iOS 필수 — App Store 심사 규정) + Google 로그인 + 이메일 폴백.** 카카오 등 추가 소셜은 2차 (Q16).
- 수용 기준:
  - 소셜(플랫폼별 필수 1종) 또는 이메일로 가입/로그인하고, 앱 재실행 시 세션이 유지된다.
  - 온보딩에서 최소 항목(성별·나이 또는 생년·키·몸무게·목표)을 입력하면 프로필로 저장되고, 이후 수정 가능하다.
- 비고: 온보딩 항목은 필수 최소치로 시작 (과다 질문은 이탈 증가). 신체정보는 개인정보 → 처리방침·동의 흐름(Q8) 필요. 인증 구현 방식(관리형 Auth vs 자체 구현)은 Q15에서 확정 — **되돌리기 비용이 큰 결정.**

### F13. 프로필 / 설정 — MVP 편입 (최소형)
- 설명: 신체정보·목표 조회/수정, 로그아웃, 계정/데이터 삭제 등 기본 설정 제공.
- 담당: **Flutter** + **FastAPI/서버 DB**(프로필 조회·수정, 계정 삭제 처리)
- 수용 기준:
  - 프로필에서 온보딩 입력값(키·몸무게·목표)을 조회·수정할 수 있다.
  - 설정에서 로그아웃 및 계정/데이터 삭제 진입이 가능하다.
- 비고: **계정/데이터 삭제는 되돌리기 어려운 작업** — 확인 다이얼로그 + 서버측 완전 삭제 처리 필요. 스토어 정책상 계정 삭제 기능은 사실상 필수. 알림·단위 전환 등 나머지 설정은 2차.

### 기능 간 의존 관계

- **기술 의존**: F5·F3 → F6 (저장할 데이터 산출) / F9 → F6 / F10 → F6. **F9와 F10은 서로 의존하지 않는다** — 둘 다 F6에만 의존.
- **계정 의존 (v0.3 신규)**: F12 → F13 (프로필은 계정 전제) / F6의 서버 동기화 → F12 (계정 없이는 동기화 불가; 로컬 저장 자체는 F12 없이 동작).
- **구현 우선순위 권고** (의존성 아님): F12(계정 기반 먼저) → F6 안정화 → F10 → F9 / F11은 콘텐츠 준비와 병행 가능.

### MVP 편입 정리 (기획팀)

- **MVP 확정선**: 스쿼트 등 소수 종목 + 실시간 코칭(F1~F4) + 렙 카운팅(F5) + 기록(F6~F7) + 캘린더(F10) + 비교 최소형(F9) + **운동 가이드 최소형(F11, 로컬 번들)** + **로그인/온보딩 최소형(F12)** + **프로필/설정 최소형(F13)**.
- **무게 경고**: 로그인 도입으로 MVP가 명백히 무거워짐 (서버·인증·서버 DB·개인정보 처리·계정 삭제·스토어 정책 준수가 한꺼번에 유입). 억제안:
  - 인증은 관리형 Auth 서비스 채택 검토 (Q15) — 토큰·소셜 연동 부담 감소, 대신 외부 의존 추가.
  - 소셜은 플랫폼별 필수 1종 + 이메일로 최소화.
  - 세션 동기화는 로컬 우선 + 백그라운드 동기화로 시작, 완전한 다기기 실시간 동기화는 2차.

## 3. 2차(확장) 기능 목록

- **운동 종목 확대**: 데드리프트·벤치프레스·런지·플랭크·푸시업 등으로 평가 규칙 + 가이드 콘텐츠 확장
- **녹화 후 정밀 리뷰** (시나리오 B — MVP에서 뺀 경우)
- **운동 기록 통계/대시보드**: F9(일간 1:1 비교)를 넘어서는 **주간·월간 추세, 부위별 빈도, 볼륨 그래프 등 장기·다차원 집계**. F10은 조회 진입점, F9는 단기 비교(입문판), 대시보드는 그 상위 확장 — 계층 관계.
- **다기기 실시간 동기화 고도화**: MVP의 백그라운드 동기화를 넘어선 즉시 동기화·충돌 해결
- **소셜 로그인 확대**: 카카오 등 국내 소셜 추가 (Q16)
- **운동 가이드 서버 CMS화**: 로컬 번들 → 서버 배포로 전환, 운동 라이브러리 대량 확장
- **운동 리마인더 알림**, 단위(kg/lb) 전환 등 설정 확장
- **루틴 추천**: 이력·목표(온보딩 프로필) 기반 추천, 프로그램 템플릿
- **소셜**: 폼 영상 공유, 챌린지, 랭킹
- **AI 코칭 코멘트 고도화**: 정형 메시지 → 개인화 자연어 피드백
- **웨어러블 연동**, 세트 간 휴식 타이머
- **모델 경량화·저사양 폴백**, 음성 핸즈프리 코칭 고도화·다국어

## 5. 열린 질문

**확정됨:**

- ~~**Q4. 회원가입/로그인 필요 여부**~~ → **"도입"으로 확정** (사용자 지시: 기존 헬스 앱 표준을 따름). 하위 결정은 Q15(인증 방식)·Q16(소셜 종류)으로 이관. **파급: FastAPI 서버 + 서버 DB가 MVP 필수로 승격.**
- **Q12. 기록 보존·이관** → 계정 도입으로 **해소 방향 확정**: 세션 기록을 서버 동기화(Q14의 권장안)하면 기기 변경 시 복원 가능. 단 Q14에서 "서버 단독"이 아닌 "로컬 우선+동기화"를 택해야 오프라인(Q10)과 양립.

**핵심 아키텍처 (먼저 답해야 나머지가 정해짐):**

1. **Q1. 추론 위치** — 온디바이스(tflite) vs 서버 vs 하이브리드?
   - 기획팀 잠정 권장: **실시간이 핵심 가치이므로 온디바이스 우선.** (서버가 MVP에 들어왔지만 이는 인증·프로필 용도 — 추론까지 서버로 옮길 이유는 아님. 영상 원본 서버 미전송 원칙 유지 권장: 프라이버시·대역폭·비용.)
2. **Q2. 실시간(A) vs 녹화 리뷰(B)** 중 MVP에 무엇을 넣나?

**범위:**

3. **Q3. MVP 지원 운동 종목 수** — 스쿼트 1종부터 검증 권장 vs 처음부터 3~6종 (가이드 콘텐츠 F11도 종목 수에 비례해 증가)
5. **Q5. 폼 판정 기준의 근거** — 문헌·트레이너 감수 각도 임계값 vs 자체 추정 (F11 가이드 내용과 일관성 필요)

**품질·비기능:**

6. **Q6. 정확도 수용 기준 수치화** — 렙 카운팅 허용 오차(%), 폼 판정 목표 정밀도, 허용 지연(ms)
7. **Q7. 타깃 기기/OS 범위** — iOS·Android 둘 다? 최소 사양? (Apple 로그인 필수 여부·소셜 구성 Q16과 연동)
8. **Q8. 프라이버시/데이터 처리** — 촬영 영상 저장 여부·보존 기간 + **온보딩 신체정보(개인정보) 처리방침·동의 흐름** (계정 도입으로 중요도 상승)
9. **Q9. 모델 확보 방식** — 사전학습 YOLO-pose 그대로 vs 헬스 동작 데이터 파인튜닝
10. **Q10. 오프라인 동작 요구** — 헬스장 네트워크 불안정 대응 (Q14 저장 전략과 직결)

**기록·비교 (F9·F10):**

11. **Q11. 비교·날짜 규칙 확정** — "어제"의 정의(달력 전날 vs 직전 세션 — 후자 잠정 권장) / "운동량" 지표 정의 / 다중 세션 집계(기본값 일 합산) / 날짜 경계·시간대 규칙 재확정

**계정·기초 기능 (v0.3 신규):**

13. **Q13. 운동 가이드 콘텐츠 확보** — 시연 미디어·설명을 자체 제작 vs 라이선스 vs 외부 소스. 저작권·제작 리소스 이슈.
14. **Q14. 세션 기록 저장 전략** — **로컬 우선 + 서버 동기화(권장)** vs 서버 단독. 오프라인(Q10)·비교/캘린더(F9·F10)·기록 이관(Q12)에 모두 영향.
15. **Q15. 인증 구현 방식** — 관리형 Auth 서비스 vs FastAPI 자체 구현(JWT 등). 개발 부담·외부 의존·비용 트레이드오프. **되돌리기 어려운 결정.**
16. **Q16. 소셜 로그인 종류 범위** — Apple/Google만 vs 카카오 포함. 타깃 시장(Q7)과 연동.
